# ブラウザ内Verilog実行の技術検証

検証日: 2026-09-19。方式選定の小規模検証に加え、Reactアプリへの統合と本番ビルドの検証まで実施。デプロイは未実施。

## 結論

Icarus VerilogのWebAssembly版をWeb Workerで実行し、命令単位の状態履歴をReactに渡す方式を第一候補とする。ブラウザ内でVerilogをコンパイルし、TD4の基本命令と状態取得が動くことをChromeで確認した。

公開済みWASMを使った実行可能性の確認まで完了。配布するエンジンのソース一式・パッチ・再現可能なビルド手順の確保は残っており、本番採用を無条件に確定した段階ではない。

## リポジトリ確認

- 開始時は`main`、`f0f4314 Initial commit`、作業ツリーに変更なし。
- 既存ファイルはMITライセンスの`LICENSE`のみ。内容を確認し、変更していない。
- 調査対象のリポジトリ内と上位ディレクトリに適用対象の`AGENTS.md`は見つからなかった。
- 現在のPowerShellでは`node`、`npm`がPATH上に存在しない。Viteプロジェクトは未構築で、`npm run build`も未実施。
- Chrome/Edgeはインストールされている。検証はChrome 153のヘッドレス実行、専用プロファイルを使用。

## 方式比較

以下の評価は公開資料と今回のIcarus実測に基づく設計判断。他方式を実行比較したベンチマークではない。

| 方式 | 利点 | この教材での課題 | 判断 |
| --- | --- | --- | --- |
| Icarus Verilog WASM | Verilog自体を実行でき、テストベンチ・エラー位置・VCDを利用できる | WASM移植の再現性、配布物の管理、履歴再生と実行の接続 | 第一候補。今回実行確認 |
| YoWASP/Yosys + DigitalJS | Verilogを回路へ変換し、その回路をシミュレーション・表示できる | 合成、形式変換、シミュレータの統合が必要。未完成コードやX値を含む挙動の検証も必要 | 代替候補。未実行 |
| Verilator / CXXRTLでC++モデルを生成してWASM化 | 明示的なクロック駆動と状態参照の構成を作れる | 編集後の回路ごとにC++生成・コンパイルが必要。ブラウザ内の追加ツールチェーンの規模が増える | 初期版では優先度低 |
| Verilogの限定構文を独自解釈 | 教材に必要なAPIを自由に設計できる | 幅、符号、並行動作、ノンブロッキング代入、X/Zなどの言語意味論を自分たちで維持する必要がある | 初期版では採用しない |

Icarus WASMの実例は[VeriSim](https://github.com/senolgulgonul/verisim)。Yosysのブラウザ利用は[YoWASP](https://yowasp.org/)、回路シミュレータは[DigitalJS](https://github.com/tilk/digitaljs)、形式変換は[yosys2digitaljs](https://github.com/tilk/yosys2digitaljs)を参照。後者の公開packageには`./core`と`./node`の入口があるので、採用する場合はブラウザ用の変換経路を確認する。

[YoWASP/yosys](https://github.com/YoWASP/yosys)は調査時に2026-03-11付のarchive表示があり、継続的に使う場合は保守元を別途確認する。Icarus WASMも第三者による移植であり、上流公式のブラウザ配布と同一視しない。

[Verilator公式概要](https://verilator.org/guide/latest/overview.html)と[Yosys CXXRTLの説明](https://yosyshq.readthedocs.io/projects/yosys/en/0.46/cmd/write_cxxrtl.html)によれば、生成されたC++モデルをドライバとともにコンパイルして利用する。完成済みTD4だけを事前にWASM化する方法では、受講者が変更したVerilogの実行にはならないため、この教材の中核には使わない。

## 実行した検証

コード: [`spikes/icarus-browser`](../spikes/icarus-browser/README.md)。Node.jsに依存しないHTML/ES Modulesの検証ページを作成した。PowerShellは静的ファイルをlocalhostに配信し、最後の検証レポートを保存するだけ。Verilogの前処理・コンパイル・実行はすべてChromeのWeb Worker内で行った。

使用した公開配布物:

- リポジトリ: `senolgulgonul/verisim`
- 固定コミット: `a275a9ac28c59db1130505973644c9a3754ec1d7`
- 配布元READMEの説明: Icarus 14.0 devel、upstream `c7530db`由来。ローカルで再ビルドして一致を確認したわけではない。
- JS/WASM 6ファイル合計: **2,994,577 bytes（約2.86 MiB、圧縮前）**。
- 最大ファイル: `ivl.wasm` 1,670,232 bytes。
- 取得したバイナリは`vendor/`に置き、Git対象から除外。固定コミット・サイズ・SHA-256を[`vendor-manifest.json`](../spikes/icarus-browser/vendor-manifest.json)に記録。

最終実行で以下の10項目がすべて成功した。期待値は検証コード内の明示的な表を使用し、CPU実装から自動生成していない。

| 項目 | 確認した内容 |
| --- | --- |
| 基本命令 | 12命令形式、JNCの成立・不成立、開始時/実行後のリセット、内部信号を含むVCD |
| キャリー | Bの15+1、MOVによるCの更新、その後のJNC |
| PC | 15番地の次が0番地になる |
| 入力履歴 | 途中の入力変更から後だけ履歴が変わる |
| 誤実装 | 加算を減算に変えると実際のCPU履歴が変わる |
| 構文エラー | 元のファイル名`td4.v`と行番号19が返る |
| 加算器 | 4ビット入力全256組の5ビット結果 |
| レジスタ | クロック立ち上がり以外と書き込み対象外では値を保持 |
| 長い履歴 | 4096命令が完走し、期待する最終状態になる |
| 中止と応答性 | 終わらないシミュレーション中にもメイン画面のタイマーが動き、Workerを終了できる |

結果の保存先: [`results.chrome.json`](../spikes/icarus-browser/results.chrome.json)。

## 性能と配信条件

最終実行のWorker内計測:

| 処理 | 時間 |
| --- | --- |
| 基本14命令の前処理・コンパイル | 約150 ms |
| 同14命令の実行・波形取得まで | 約199 ms |
| 入力を変更した14命令の再計算 | 約237 ms |
| 4096命令の前処理・コンパイル | 約138 ms |
| 同4096命令の実行・波形取得まで | 約260 ms |

4096命令のVCDは536,706 bytes。計測にはWorkerの起動前やJSモジュールのimport時間、インターネットからの初回ダウンロード、Reactの描画時間を含まない。同じPC上のlocalhostによる単発値であり、講義端末やネットワークでの性能保証ではない。

特別なCOOP/COEPヘッダなし、`crossOriginIsolated: false`で成功した。この配布物・検証構成ではSharedArrayBuffer前提の環境分離は不要だった。WASMを`application/wasm`、JSを`text/javascript`で同一オリジンから配信した。

[Cloudflare Pagesの単一資産上限は25 MiB](https://developers.cloudflare.com/pages/platform/limits/)で、今回の各ファイルは範囲内。Pagesへの実デプロイは未検証。

## 判明した統合上の注意

VeriSimの例にあるコンパイラ設定`module:system.vpi`は、今回の配布物では成功時にも`dynamic linking not enabled`という診断を発生させた。

コンパイラ側の指定だけを外すと、実行時に`$display`等が未定義になった。最終コードではコンパイラ設定から外し、**実行側を`vvp -m system /program.vvp`にする**ことで静的リンク済みのタスクを登録した。エラー文字列を隠す処理は入れていない。成功時にエラー診断がないことも再検証した。

`callMain`が終了したインスタンスの再利用は前提にせず、1要求ごとにWorkerと各WASMインスタンスを作る。入力履歴の再実行は動いたが、vvpを途中停止して任意入力を注入・再開するAPIは今回確認していない。

## 本番採用前に残ること

1. **WASMの再現性と配布準備**: 配布元はIcarus由来のGPLと記載している。WASM移植パッチとビルド手順を含む対応ソース一式を確保し、再ビルドする。今回取得したREADMEは上流コミットを挙げているが、参照先だけで移植変更を再現できることは未確認。ライセンス表示とソース提供方法を含めて配布方法を確定する。既存のMIT `LICENSE`は変更していない。
2. **TD4の厳密な互換性**: 原著回路との照合、非標準符号を含む扱い、全入力・状態の網羅的比較は未実施。今回の成功を完全互換の証明とはしない。
3. **本体との接続**: 初期版で実装・検証済み。React/ViteのWorkerとWASMアセットの配置、状態トレースの形式、X/Zの表示、エラー行からエディタへの移動が動作した。詳細は下記の統合検証を参照。
4. **講義端末**: Edge/Firefox/Safari、低速端末、初回ダウンロード、長時間の繰り返し実行時のメモリ使用量を確認する。現段階の対象ブラウザ案はデスクトップChrome/Edgeだが、実測はChromeのみ。
5. **配信**: 本番ビルドとローカルの静的プレビューは成功。PagesプレビューでMIME、パス、WASM読込と再読込を確認する。

Icarus移植の再現性を確保できない場合は、Yosys + DigitalJSを次の検証対象とする。CPUの命令仕様を独自化してもエンジンの配布・実行の問題は解決しないため、TD4互換の方針は維持する。

## Reactアプリの統合検証

同日、Node.js 24.21.0 / Vite 7 / React 19で初期版を実装。`npm run build` が成功した。エディタは課題画面を開くときに読み込み、初期JSは約256 KB、エディタを含む課題画面は約408 KB（いずれも圧縮前）。WASMは固定済みの6資産を同一オリジンから読み込む。

`npm test` の5件で、入力履歴の分岐、X/Z、途中終了トレース、実行上限・ROMの検査、保存形式を確認。`npm run test:e2e` の6件は、ビルド済みの静的サイトをChromeで開いて次を確認した。

| 検証 | 結果 |
| --- | --- |
| 受講者の一連の操作 | 完成例のLED、初期加算器の失敗、3課題の完成、自己CPU実行、再読み込み後の進捗を確認 |
| 課題の実Verilog検証 | 加算器256ケース、レジスタ50ケース、PC34ケースが成功 |
| ROM・入力 | ROM変更時に古い実行を無効化、途中入力の変更・巻き戻し後の変更、分岐サンプルを確認 |
| 誤実装 | 加算器の出力をXにすると、自己CPUのB・OUTにもXが現れることを確認 |
| エラーからの復帰 | 元ファイルの行番号付き構文エラー、無限ループの手動中止、修正後の再実行を確認 |
| モジュール接続後の命令 | 基本12命令形式とJNCの成立・不成立を、14命令分の明示した期待状態と比較 |
| 保存ファイル | JSONの書き出し、読み込み、再検証、取り消し、不正ファイルの拒否を確認 |
| 小さい画面 | 幅390pxで横方向にはみ出さないことを確認。PCとモバイル幅のスクリーンショットも目視確認 |

アプリのブラウザテストは [`tests/app.spec.ts`](../tests/app.spec.ts)、ユニットテストは [`src/cpu.test.ts`](../src/cpu.test.ts)。Chrome以外の実行、15秒のタイムアウト到達、Pages配信、授業端末の性能はこの統合テストには含まない。スパイクの4096命令検証は上記の別結果を参照。
